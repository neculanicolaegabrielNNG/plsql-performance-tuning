# PL/SQL performance tuning: row-by-row to set-based

An Oracle case study. A slow monthly report over a few million rows gets faster one measured step at a time, and a correctness check guards each step. All data is synthetic and generated by the scripts.

## Problem

A fictional shop with `CUSTOMERS`, `PRODUCTS`, `ORDERS`, `ORDER_ITEMS` and `PAYMENTS` (200k / 5k / 5M / ~15M / 5M rows at full scale). The report lists the top customers of the month with their order total and last payment date, written to `REPORT_TOP_CUSTOMERS`.

The first version, `REPORT_TOP_CUSTOMERS_SLOW`, returns the right answer and has the usual problems of reporting code: a row-by-row cursor with SELECTs inside (N+1), `TRUNC`/`TO_CHAR` on columns in `WHERE`, `SELECT *`, no indexes on join keys, correlated subqueries, a COMMIT per row and no optimizer statistics. Its cost grows quadratically with data volume.

The goal is to make it fast without changing its result, with a benchmark showing the speed-up and a MINUS check showing the result is the same.

## What I changed

| Cause | What the plan / counters show | Step | Change |
|---|---|---|---|
| No index on `ORDERS.CUSTOMER_ID`, `PAYMENTS.ORDER_ID` | `TABLE ACCESS FULL` in statements run once per customer | 2 | `ORDERS(customer_id, order_date)`, covering `ORDERS(order_date, status, customer_id, order_id)`, `PAYMENTS(order_id)` |
| `TO_CHAR`/`TRUNC(order_date)` in `WHERE` | `ORDER_DATE` only in filter predicates | 3 | half-open range `order_date >= :start AND order_date < :next_start` |
| N+1 loop, `SELECT *`, correlated subqueries, COMMIT per row | high `Starts` on the same cursors, lots of redo | 4 | one `INSERT ... SELECT` with joins, `GROUP BY`, `ROW_NUMBER()`; last payment only for the top N |
| Row-level PL/SQL done row by row | one context switch per row | 5 | `BULK COLLECT ... LIMIT` + `FORALL`, one COMMIT |
| No statistics | "dynamic sampling used", E-Rows far from A-Rows | 6 | `DBMS_STATS`, `SIZE AUTO`, `NO_INVALIDATE => FALSE`; hints only with evidence |
| Same month aggregated on every run | join + aggregate on each call | 7 (optional) | materialized view (7a) or monthly partition pruning (7b) |

## How to run

Requirements: Oracle 19c or later (partitioning in 7b is a licensed option), SQL*Plus or SQLcl, and Python 3.9+ for the optional runner. The schema needs `CREATE TABLE`, `CREATE PROCEDURE`, `CREATE SEQUENCE` (plus `CREATE MATERIALIZED VIEW` for 7a) and read access to `V$MYSTAT`, `V$STATNAME`, `V$SQL`, `V$SQL_PLAN`, `V$SQL_PLAN_STATISTICS_ALL`, `V$SESSION`. A DBA can run [`01_schema/00_create_user_optional.sql`](01_schema/00_create_user_optional.sql), which prompts for the password and doesn't store it.

Run every script from the project root, because the spool paths are relative.

```sql
@01_schema/01_create_tables.sql
@05_benchmark/00_install_bench_package.sql
@02_data_generation/run_all.sql          -- prompts for SCALE (default 0.05, ~1.26M rows)

@03_slow_version/01_report_top_customers_slow.sql
@03_slow_version/02_run_slow.sql
```

SLOW's work grows with *(customers in the month) × (rows in ORDERS + PAYMENTS)*. Start at `SCALE = 0.01`, time `02_run_slow.sql`, then scale up. At `SCALE = 1`, benchmark V2 and later only.

Indexes, statistics and the MV change the plans of every version, so each version is benchmarked right after its own step and labelled with the schema state:

| `@04_optimization_steps/07a_optional_materialized_view.sql` | V7 | `after_step7` |

From SQL (results in `BENCHMARK_RUNS`):

```sql
@05_benchmark/02_benchmark_version.sql V4 after_step4
@05_benchmark/03_capture_plan.sql V4          -- ALLSTATS LAST -> results/plans/V4_plan.txt
@05_benchmark/04_show_results.sql             -- medians per label and version
```

From Python (thin mode, no Oracle Client):

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate    Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env                  # Windows: copy .env.example .env, then fill it in
python python/benchmark.py --label after_step1 --versions slow,v1
python python/benchmark.py --label after_step4 --versions v4
python python/benchmark.py --chart-only   # rebuild results/results.csv and the chart
```

Options: `--runs` (5), `--warmup` (1), `--top-n`, `--month YYYY-MM`, `--linear` (the default chart is log scale). Each step has a `*_rollback.sql`. Roll back in reverse order.

Correctness, required before any timing counts:

```sql
@05_benchmark/01_verify_correctness.sql
```

It runs every installed version, compares it with SLOW using MINUS both ways plus a row count, prints PASS/FAIL and writes `results/correctness_output.txt`.

Where to run it:
- **Oracle Database Free** (container or VM): best for repeatable timings. The usual DSN is `localhost:1521/FREEPDB1`.
- **Autonomous Database, Always Free**: runs everything, including step 7. Set `ORACLE_DSN` (plus `ORACLE_WALLET_DIR` for mTLS) and use the `_tp` or `_low` service so execution stays serial. Storage is limited, and `FLUSH BUFFER_CACHE` isn't available, so you only get warm-cache numbers.
- **Live SQL**: only for reading plans at SCALE 0.001–0.002. SQL*Plus commands (`@`, `ACCEPT`, `DEFINE`, `SPOOL`) may not work, so paste the statements and replace `&scale` by hand. The Python runner can't connect to it.

## Design notes

**Scripts.** SQL*Plus/SQLcl with `@@`, `ACCEPT`, `DEFINE`, `COLUMN ... NEW_VALUE` and `SPOOL`, run from the project root. Every script sets `SQLBLANKLINES ON`. Comments contain no ampersand, because SQL*Plus substitutes it even inside comments. `benchmark.py` has a small `.env` reader so `requirements.txt` stays at three packages, and real environment variables win.

**Data model.**
- `ORDER_ITEMS` has a composite PK `(order_id, line_no)`, so its index also serves lookups by order. Without it the N+1 slow version would scan 15M lines per customer and never finish. The missing join-key indexes are still there to see on `ORDERS.CUSTOMER_ID` and `PAYMENTS.ORDER_ID`.
- FKs are declared as constraints, not indexes, so the baseline really is PKs only. They are disabled during the bulk load, because with FKs enabled Oracle ignores `APPEND`, and re-enabled with `VALIDATE`.
- `ORDERS.NOTES` is filler, so `SELECT *` and full scans cost what they would on a real table.
- Extra tables: `DATASET_INFO`, the stage table for the row-by-row versions, `BENCHMARK_RUNS`, and `STATS_BACKUP` (created by step 6).

**Data generation.**
- One parameter, `scale`, with 0 < SCALE ≤ 1 enforced by a CHECK. Small floors (100 customers, 20 products, 2,500 orders) keep tiny scales usable.
- 24 full months ending with the current month, so the report month is complete. A few dates land after today, which doesn't matter for fake data. The report month is stored in `DATASET_INFO`, so benchmarks don't drift when the calendar moves on.
- Skew: 2% whale customers get 30% of the orders, and product popularity follows a squared uniform. Order status mix: DELIVERED 55%, SHIPPED 15%, PAID 10%, PENDING 8%, CANCELLED 8%, RETURNED 4%, independent of order age. Payment status follows the order status.
- Reproducibility: a fixed `DBMS_RANDOM` seed per table (42, +1, +2) where rows come from the generator in a fixed order. `ORA_HASH(key, buckets, seed)` for child tables, where row order depends on the plan. The session is forced serial.
- The row generator is two `CONNECT BY LEVEL <= 5000` cross-joined, because one `CONNECT BY` of 5M rows can hit ORA-30009. `order_id` is assigned in `order_date` order, as in a real table.
- Statistics are deleted after the load (12c+ gathers them online), so the baseline has a defined state and step 6's rollback can return to it.

**Report semantics, identical in all versions.**
- Counted orders: PAID, SHIPPED or DELIVERED, with `order_date` inside the report month.
- Order value: `SUM(ROUND(quantity * unit_price * (1 - discount_pct/100), 2))`, rounded per line like an invoice, so SQL and PL/SQL sums match exactly. Shipping is excluded.
- Last payment: the latest COMPLETED payment in any month, NULL if there is none.
- Ranking: `orders_total DESC, customer_id ASC`. The tie-break makes `rank_no` deterministic, which the MINUS check needs.
- Each version deletes and rewrites only its own `GENERATED_BY` rows and commits at the end, for parity with SLOW. In real code the caller would own the transaction.

**Steps.**
- One change per step: V1 only adds instrumentation, V2 only the indexes, V3 only the predicates. V4 removes several mistakes at once, because they go away together with the loop.
- V5's row-level logic is a data-quality guard plus building the record. I expect it to be about as fast as V4.
- V6 has no hints. A hint needs captured E-Rows/A-Rows evidence, and the decision rule is in the script.
- 7a uses COMPLETE refresh (fast refresh can't handle `COUNT(DISTINCT)`) and refuses a stale MV. 7b works on a partitioned copy, so ORDERS and the other versions are untouched.

**Benchmark.**
- Two independent paths, `PERF_BENCH` (SQL) and `benchmark.py` (CSV + chart), measure the same things: elapsed time and V$MYSTAT deltas.
- Plans are captured in a separate run with `statistics_level = ALL`, which works like `GATHER_PLAN_STATISTICS` for SQL inside the procedures. These runs are never timed.
- The chart is log scale by default, because SLOW can be orders of magnitude slower.
- `results/*.csv` and `results/*.png` are git-ignored. The README links the chart from `docs/img/`, where only a checked copy goes.

## Limitations

- **Synthetic data.** Uniform dates, a simple whale/regular skew, and status independent of age. Real data has correlations that affect estimates.
- **Single user, warm cache.** No concurrency or I/O contention. Cold-cache behaviour is described in [`docs/benchmark_methodology.md`](docs/benchmark_methodology.md) but not measured.
- **Numbers depend on the environment.** Compare versions on one machine. Across environments, consistent gets are more reliable than elapsed time.
- **Cumulative schema state.** Earlier versions get faster after later schema changes. The labels make this visible, but it is still part of the numbers.
- **SLOW is impractical at full scale.** Compare all versions at a smaller SCALE.
- **Step 7 is optional.** Partitioning needs a licence on-prem, and the MV needs a refresh strategy and tolerance for stale data.
- **Untested.** Nothing has been run against a database yet, and `py_compile` hasn't been run on `benchmark.py`. Run both before the first benchmark.
